## 1. 文档信息

| 项目 | 内容 |
| --- | --- |

| 编制日期 | 2026-08-17 |

## 2. 当前产品形态

当前系统已经具备三个相对独立的管理对象：

1. **sing-box 节点**：管理公网入口协议、端口、凭据、节点名称和客户端导入链接。
2. **VPNGate 出口**：管理 VPNGate 节点、国家、IP 类型、本地代理端口、OpenVPN 进程和 TUN 设备。
3. **节点组合**：把某个 sing-box 节点绑定到主机网络或指定 VPNGate 出口。

当前数据路径为：

```text
主机直连：
客户端 -> sing-box 入站 -> direct -> 主机网络 -> Internet

VPNGate 出口：
客户端 -> sing-box 入站 -> 127.0.0.1:7928/7929/... -> tun0/tun1/... -> VPNGate -> Internet
```

当前主要代码边界：

| 文件 | 当前职责 | 规模/特征 |
| --- | --- | --- |
| `vpngate_manager.py` | 配置、节点、OpenVPN、出口、API、Web UI、后台任务 | 约 7300 行，职责过多 |
| `singbox_manager.py` | sing-box 配置生成、校验、服务控制、客户端链接 | 约 700 行 |
| `proxy_server.py` | 本地 HTTP/SOCKS5 代理及指定 TUN 出口 | 线程式实现 |
| `vpn_utils.py` | DNS、网络、诊断和辅助操作 | 通用工具与业务诊断混合 |
| `install.sh` | 安装、升级、服务文件、CLI 管理器 | 约 1300 行，包含嵌入式 Python |
| `tests/test_singbox_manager.py` | sing-box 和部分出口单元测试 | 已覆盖核心配置，但系统测试不足 |

## 3. 优化目标

下一阶段不以增加更多协议为第一目标，而是确保已有功能满足以下要求：

- **稳定**：任一 VPNGate 节点失败、OpenVPN 退出或 sing-box 重载失败时，不导致整个管理服务失控。
- **正确**：Web UI 显示的节点、端口、出口、客户端链接与实际运行配置一致。
- **可恢复**：配置应用失败时自动回滚，重启系统后恢复用户声明的运行状态。
- **可诊断**：能够回答“哪一段链路失败、失败原因是什么、最后一次成功是什么时候”。
- **安全**：本地代理不误暴露公网，凭据不进入日志，管理操作具备明确权限边界。
- **可维护**：拆分超大模块，建立数据模型、服务层和 API 层边界。
- **可发布**：安装、升级、回滚和 CI 检查具备可重复流程。

## 4. 问题与优先级

### 4.1 P0：发布前必须解决

| 编号 | 问题 | 影响 | 优化方向 |
| --- | --- | --- | --- |
| P0-01 | 运行状态主要保存在进程内字典和线程对象中 | 服务重启后额外 VPN 出口不会自动恢复，状态可能与进程不一致 | 建立声明状态与运行状态分离的协调器 |
| P0-02 | 保存配置、生成 sing-box JSON、重载服务不是完整事务 | 中途失败可能留下“页面已保存但服务未生效”状态 | 校验、备份、原子替换、重载、健康检查、失败回滚 |
| P0-03 | OpenVPN/TUN/本地代理的启动与停止分散 | 容易残留进程、路由表、端口或 TUN 设备 | 为每个出口建立统一生命周期状态机 |
| P0-04 | 安装脚本同时承担安装、更新和交互管理 | 平台差异和升级路径难以测试，失败点不清晰 | 拆分安装阶段并提供幂等检查和失败摘要 |
| P0-05 | 配置文件缺少显式版本和迁移记录 | 旧安装升级后容易继承不完整字段 | 引入 `schema_version` 和顺序迁移函数 |
| P0-06 | README 对 `7928` 是否需要公网放行存在矛盾描述 | 用户可能错误开放本地代理 | 文档、安装提示和运行检测统一为回环端口不开放 |
| P0-07 | 缺少真实进程级链路回归测试 | 单元测试通过仍可能出现客户端无法连接 | 增加 sing-box check、临时端口和代理链集成测试 |

### 4.2 P1：核心体验和可维护性

| 编号 | 问题 | 影响 | 优化方向 |
| --- | --- | --- | --- |
| P1-01 | `vpngate_manager.py` 同时包含 HTML、API 和网络控制 | 修改任一页面或接口都可能影响核心连接逻辑 | 按领域拆分 Python 包和静态资源 |
| P1-02 | Web UI 保存动作与运行状态反馈不够一致 | 用户不知道“已保存”“已应用”“已连通”的区别 | 引入草稿、已应用、运行中、异常四层状态 |
| P1-03 | 多出口缺少完整健康指标 | 只能看到进程是否运行，不能确认出口可用 | 每个出口独立探测公网 IP、延迟和最后错误 |
| P1-04 | 节点组合依赖出口 ID，但删除/禁用时联动提示不足 | 可能产生失效引用 | 删除前影响分析，禁止悬空引用或支持迁移到直连 |
| P1-05 | 客户端导入链接只做格式级生成 | 链接格式正确但服务端口、协议能力可能不可用 | 保存后做监听检测，并提供协议级测试结果 |
| P1-06 | 后台线程大量使用宽泛异常捕获 | 异常被吞掉后只能看到功能停止 | 分类异常、结构化日志、线程心跳和自动拉起策略 |
| P1-07 | API 缺少统一错误码和任务模型 | 长操作阻塞请求，前端难以稳定展示进度 | 长任务异步化，统一错误码和任务状态 API |

## 5. 目标架构

### 5.1 分层结构

建议逐步调整为以下目录，不要求一次性重写：

```text
aimilivpn/
├── api/
│   ├── auth.py
│   ├── nodes.py
│   ├── singbox.py
│   ├── vpn_exits.py
│   └── combinations.py
├── domain/
│   ├── models.py
│   ├── validation.py
│   └── errors.py
├── services/
│   ├── node_catalog.py
│   ├── openvpn_runtime.py
│   ├── vpn_exit_runtime.py
│   ├── singbox_runtime.py
│   └── reconciliation.py
├── infrastructure/
│   ├── config_store.py
│   ├── process.py
│   ├── routing.py
│   └── diagnostics.py
├── web/
│   ├── index.html
│   ├── app.js
│   └── app.css
└── main.py
```

拆分原则：

- API 层只负责认证、解析请求和返回响应，不直接操作进程或路由。
- 服务层负责业务用例和生命周期协调。
- 基础设施层封装文件、子进程、系统服务、路由和网络探测。
- 领域模型统一进行配置验证，Web UI 与后端共享字段定义。
- 迁移期间保留 `vpngate_manager.py` 作为兼容入口，逐个移动功能，避免大爆炸式重写。

### 5.2 声明状态与运行状态

配置中保存用户希望系统达到的状态：

```json
{
  "schema_version": 2,
  "singbox_nodes": [],
  "vpn_exits": [],
  "combinations": [],
  "desired_state": {
    "singbox": "running",
    "vpn_exits": {
      "default": "running",
      "usa": "stopped"
    }
  }
}
```

运行状态由协调器实时产生，不直接当作配置保存：

```json
{
  "component": "vpn_exit:usa",
  "phase": "healthy",
  "pid": 1234,
  "tun": "tun1",
  "proxy_endpoint": "127.0.0.1:7929",
  "egress_ip": "203.0.113.10",
  "last_transition_at": 0,
  "last_healthy_at": 0,
  "error_code": "",
  "error_message": ""
}
```

协调器周期性比较两者，并执行最小动作使运行状态接近声明状态。这样可统一处理服务重启、进程意外退出和节点切换。

### 5.3 VPN 出口状态机

每个 VPNGate 出口使用一致状态：

```text
stopped
   |
   v
preparing -> connecting -> tunnel_ready -> proxy_ready -> healthy
   |             |              |              |            |
   +-------------+--------------+--------------+----------> failed
                                                               |
                                                               v
                                                          retry_wait
```

状态转换要求：

- `preparing`：检查端口、TUN 名称、路由表、节点配置和权限。
- `connecting`：启动 OpenVPN，捕获明确的超时和认证错误。
- `tunnel_ready`：确认 TUN 存在并具有地址。
- `proxy_ready`：确认本地代理端口仅在回环地址监听。
- `healthy`：通过该本地代理获取公网 IP 成功。
- `failed`：记录结构化错误并清理本次创建的资源。
- `retry_wait`：指数退避并设置最大频率，避免无限快速重启。

## 6. 重点优化设计

### 6.1 配置事务与回滚

所有“保存并应用”操作使用同一流程：

1. 解析请求并只接受白名单字段。
2. 使用领域模型完成类型、端口、引用和协议校验。
3. 在临时目录生成完整候选配置。
4. 执行 `sing-box check` 和内部一致性检查。
5. 备份当前配置及其校验和。
6. 使用 `fsync + os.replace` 原子替换。
7. 重载或重启目标服务。
8. 检查监听端口、进程状态和必要链路。
9. 健康检查失败则恢复备份并再次启动旧配置。
10. 只有全部成功后才更新 `last_apply_at` 和 API 成功响应。

API 应区分以下结果：

- `saved`：配置已持久化但未应用。
- `applied`：目标服务已加载新配置。
- `healthy`：真实链路探测成功。
- `rolled_back`：新配置失败，已恢复旧配置。

### 6.2 sing-box 节点管理

- 节点 ID 永久不变，名称允许重复但 UI 应提示；客户端链接始终使用节点自己的名称。
- 端口在全部 sing-box 入站、Web UI 和本地出口代理之间全局唯一。
- 后端统一生成客户端链接，前端不得自行拼接协议 URI。
- API 返回 `name`、`protocol`、`server`、`port`、`endpoint` 和 `uri`，页面分别展示服务器端点与导入链接。
- Reality、TUIC、Hysteria2、AnyTLS 保存时检查密钥或证书材料是否存在。
- 对 TLS 自签名协议明确标记客户端需要的安全参数，并允许后续接入用户证书。
- 删除节点前展示对应组合关系；删除后不能保留悬空组合。

### 6.3 VPNGate 多出口

- `tun_name` 和 `route_table` 不依赖列表顺序动态生成，改为创建时分配并持久化。
- 启动前检查 TUN 名称、路由表、代理端口是否被其他进程占用。
- 每个出口拥有独立的停止事件、进程句柄、日志上下文和健康状态。
- 默认出口与额外出口使用同一运行时抽象，去除大量 `if id == default` 分支。
- 切换节点时先建立新隧道并验证，再替换旧隧道；资源允许时采用短暂双运行，降低断流。
- 出口删除必须依次停止代理、终止 OpenVPN、清理路由规则、删除临时配置并验证资源消失。
- 国家和 IP 类型是筛选策略，不应直接等同于固定节点；支持“策略自动选择”和“手动固定节点”两种模式。

### 6.4 节点组合

- 组合模型只保存 `singbox_node_id -> egress_id`，不复制本地端口等派生字段。
- `direct` 作为内置出口对象参与统一校验。
- 保存组合时检查入口和出口均存在、启用状态合理、引用无循环。
- 出口停用时，明确显示受影响入口数量，不自动静默切换到其他出口。
- 提供批量操作：多个入口选择同一出口、全部切回主机网络。
- 组合页面直接显示端到端路径和健康结果：

```text
入口名称 :4433 -> 美国出口 :7929 -> tun1 -> VPNGate US -> 198.51.100.20
```

### 6.5 服务生命周期

- systemd 使用 `Restart=on-failure`、合理的 `RestartSec` 和启动限速。
- OpenRC 使用 `supervise-daemon`，确认 pidfile 与实际进程一致。
- AimiliVPN 收到 SIGTERM/SIGINT 时执行有界清理，不依赖 daemon 线程被直接终止。
- 禁止用进程名宽泛杀死所有 OpenVPN；只操作当前实例创建并记录的 PID。
- 服务启动完成条件不是 HTTP 端口打开，而是配置加载完成、后台协调器启动且状态接口可用。
- sing-box 重载根据 init 系统映射为受支持动作，动作后必须再次查询运行状态。

### 6.6 安装与升级

将安装脚本划分为可单独验证的阶段：

```text
preflight -> packages -> source -> openvpn -> sing-box -> config migration
          -> service files -> start -> health check -> summary
```

具体要求：

- 每个阶段输出固定编号和成功/失败状态，不使用依赖终端能力的光标控制码。
- 重复执行安装脚本必须幂等，不覆盖用户凭据、节点和组合配置。
- 下载 sing-box 时校验版本、架构和 SHA256；版本应可固定，不默认追踪不确定的最新版本。
- 升级前创建配置备份并记录当前 Git 提交；升级失败可以恢复代码和配置。
- 不在管理命令中直接执行无范围限制的仓库清理。
- 提供 `--non-interactive`、`--branch`、`--install-dir` 和 `--skip-start` 参数。
- 安装结束以表格输出 Web UI 地址、公开入口端口、内部回环端口和各服务状态。

### 6.7 Web UI

信息架构保持三个独立页面：

- **sing-box 节点**：只处理公网入口和客户端信息。
- **VPNGate 出口**：只处理 VPN 节点、TUN、本地端口和出口健康。
- **节点组合**：只处理入口到出口的绑定关系。

交互优化：

- 列表页直接显示名称、协议/国家、端口、运行状态、健康状态和最近错误。
- 编辑使用明确的保存状态：未保存、保存中、应用中、已生效、回滚成功、失败。
- 删除动作必须显示受影响对象，不能仅依赖浏览器原生确认框。
- 客户端区域把“服务器端点”和“导入链接”分开，复制后给出目标节点名称。
- 长任务返回任务 ID，页面轮询或使用事件流显示阶段进度。
- 小屏幕使用列表布局，避免固定列宽导致名称、端点和操作按钮重叠。
- 所有错误保留错误码，并提供可复制的诊断摘要。

### 6.8 安全

- `7928/7929/...` 默认必须绑定 `127.0.0.1`，启动后检查实际监听地址；检测到公网监听时显示高危告警。
- Web UI 默认建议绑定受控地址；若监听公网，建议增加 HTTPS 反向代理或用户自有证书。
- 登录密码使用带盐的现代密码哈希，不继续保存可逆或明文凭据。
- Session Cookie 设置 `HttpOnly`、`SameSite=Strict`；在 HTTPS 下设置 `Secure`。
- 所有修改类接口增加 CSRF 防护和请求体大小限制。
- 私钥、密码、代理认证、完整客户端 URI 不写入普通日志。
- 配置文件权限统一为 `0600`，目录限制为管理员可读。
- 子进程仅使用参数数组，不拼接 shell 命令；服务动作和文件路径使用白名单。
- 增加登录限速、失败退避和会话失效机制。

### 6.9 可观测性和诊断

日志采用结构化字段：

```json
{
  "time": "2026-08-17T00:00:00Z",
  "level": "ERROR",
  "component": "vpn_exit",
  "object_id": "usa",
  "operation": "connect",
  "error_code": "VPN_EXIT_TIMEOUT",
  "message": "OpenVPN initialization timed out",
  "duration_ms": 35000
}
```

建议指标：

- VPNGate 拉取成功率、候选数、测速成功率和耗时。
- 每个出口的启动次数、失败次数、当前出口 IP、连接时长和最后健康时间。
- sing-box 重载次数、失败次数、当前入站数量和监听状态。
- 本地代理活动连接数、失败数和连接时长。
- 后台任务心跳、最近成功和连续失败次数。

诊断页面按链路分段：

```text
客户端端口监听 -> sing-box 配置 -> sing-box 出站
-> 本地代理监听 -> TUN 设备 -> 策略路由 -> 公网出口
```

每一段只返回 `healthy/degraded/failed/unknown`、时间和用户可理解的原因。

## 7. 数据迁移方案

### 7.1 版本字段

在 `ui_auth.json` 或后续独立配置文件中增加：

```json
{
  "schema_version": 2,
  "migrated_at": 0,
  "migrated_from": 1
}
```

### 7.2 迁移规则

1. 读取配置时先备份原文件，备份名包含版本和时间。
2. 迁移函数必须按 `v1 -> v2 -> v3` 顺序执行，禁止跨版本猜测。
3. 旧 `singbox` 扁平字段迁移为一个默认节点。
4. 缺少节点名称时使用协议名加序号生成，保证同协议节点可区分。
5. 缺少组合时默认绑定 `direct`，不得自动改为 VPNGate。
6. 旧默认出口保留 `7928/tun0`；额外出口保留已分配端口、TUN 和路由表。
7. 迁移后执行完整验证；失败则继续使用旧文件并阻止服务应用错误配置。

## 8. 测试方案

### 8.1 单元测试

- 所有协议的配置生成、凭据校验和客户端 URI。
- IPv4、IPv6、域名、特殊字符、中文节点名称和自定义端口。
- sing-box 节点、VPN 出口、组合的增删改查和引用完整性。
- 端口冲突、重复 ID、失效引用和配置迁移。
- systemd/OpenRC 服务动作映射和失败分支。
- VPN 出口状态机的每个状态转换和清理路径。

### 8.2 集成测试

- 使用临时目录生成配置并执行真实 `sing-box check`。
- 启动临时 sing-box 入站，确认端口监听和客户端握手。
- 使用本地模拟 HTTP 代理验证 `sing-box -> local proxy` 路径。
- 使用网络命名空间和虚拟接口验证多个 TUN/路由表互不串流。
- 模拟 OpenVPN 进程退出，确认协调器清理并按策略重试。
- 模拟 sing-box 新配置失败，确认旧配置自动恢复。

### 8.3 安装测试

CI 或测试机覆盖：

| 系统 | init | 安装 | 重复安装 | 升级 | 卸载 |
| --- | --- | --- | --- | --- | --- |
| Debian stable | systemd | 必测 | 必测 | 必测 | 必测 |
| Ubuntu LTS | systemd | 必测 | 必测 | 必测 | 抽测 |
| Alpine stable | OpenRC | 必测 | 必测 | 必测 | 必测 |

安装日志必须检查不存在原样 ANSI 控制序列、Python traceback 和未处理的服务错误。

### 8.4 端到端验收

至少构建以下场景：

1. VLESS A 使用主机网络。
2. VLESS B 使用 VPNGate 日本出口 `7928/tun0`。
3. Hysteria2 C 使用 VPNGate 美国出口 `7929/tun1`。
4. 三个客户端同时访问出口 IP 检测服务，结果符合组合关系。
5. 切换日本出口节点后，A 和 C 不受影响，B 在允许窗口内恢复。
6. 重启服务器后，三个入口和声明为运行的出口自动恢复。

## 9. 分阶段实施计划

### 阶段 0：基线冻结与问题复现（1-2 个工作日）

- 固定当前配置样例和主要 API 响应。
- 建立 Debian、Alpine 两套最小测试环境。
- 记录当前安装、重启、多出口和客户端连接的可复现结果。
- 修正 README 关于回环代理端口的矛盾说明。

退出标准：当前已知问题都有复现步骤，测试环境能够重复安装当前版本。

### 阶段 1：配置与生命周期可靠性（3-5 个工作日）

- 引入配置版本和迁移器。
- 实现原子配置应用、健康确认与失败回滚。
- 实现统一 VPN 出口状态机和资源清理。
- 重启时根据声明状态恢复 sing-box 和 VPN 出口。

退出标准：故意提交错误配置、杀死 OpenVPN、杀死 sing-box 后均能得到可预测状态，并且不会遗留路由或端口。

### 阶段 2：模块拆分与 API 统一（4-7 个工作日）

- 抽离配置存储、进程、路由、sing-box 和 VPN 出口服务。
- API 使用统一响应、错误码和任务状态。
- 把 HTML、CSS、JavaScript 从 Python 字符串移到静态文件。
- 保持现有 URL 和配置兼容。

退出标准：`vpngate_manager.py` 只保留启动和兼容入口，核心功能有独立模块测试。

### 阶段 3：Web UI 与诊断（3-5 个工作日）

退出标准：用户可以仅通过 Web UI 定位入口、sing-box、本地代理、TUN 或 VPNGate 中的具体故障段。

### 阶段 4：安装、CI 与发布（3-5 个工作日）

- 拆分幂等安装阶段并增加升级回滚。
- 建立 Python、Shell、JavaScript、sing-box 配置和安装矩阵检查。
- 完成端到端场景和发布清单。
- 更新 README、FAQ、升级和恢复文档。

退出标准：Debian/systemd 与 Alpine/OpenRC 均通过首次安装、重复安装、升级、重启和卸载测试。

## 11. 发布门槛

准备发布稳定版本前，必须全部满足：

- 配置应用失败能够自动回滚，旧服务保持可用。
- 同协议多个节点的名称、地址、端口和客户端链接完全独立。
- 多个 VPNGate 出口同时运行时，出口 IP 不串流。
- 删除、停用、切换出口不会留下 OpenVPN、TUN、路由表或监听端口。
- 服务和系统重启后能恢复声明为运行的对象。
- `7928/7929/...` 未监听公网，安装和 README 不要求开放这些端口。
- Debian/systemd 和 Alpine/OpenRC 的安装升级测试通过。
- Python 单元测试、JavaScript 语法、Shell 语法、sing-box check 和端到端测试全部通过。
- 日志中不存在私钥、密码、完整认证 URI 和访问令牌。
- Web UI 能明确区分配置已保存、服务已应用和链路已健康。

## 12. 风险与控制

| 风险 | 可能后果 | 控制措施 |
| --- | --- | --- |
| 一次性重构超大主文件 | 引入难以定位的回归 | 逐模块迁移，保持兼容入口，每步单独提交和测试 |
| 多 TUN 策略路由在发行版间不同 | 某些系统出现无流量或串流 | 网络命名空间测试，系统能力预检，按平台封装 |
| VPNGate 免费节点本身不稳定 | 自动化测试波动 | 核心测试使用本地模拟服务，公网节点只做非阻断抽测 |
| sing-box 版本变化 | 配置字段失效 | 固定受支持版本，升级前运行协议矩阵和 `sing-box check` |
| 配置迁移破坏旧安装 | 用户节点或凭据丢失 | 迁移前备份、版本化迁移、失败不覆盖原文件 |
| 自动恢复形成重启风暴 | CPU/网络被持续占用 | 指数退避、最大重试频率、熔断和人工恢复入口 |

## 13. 建议的首个迭代

第一轮只处理最影响可用性的闭环，不同时进行 UI 大改：

1. 修正 README 中关于本地代理端口放行的错误说明。
2. 引入 `schema_version` 和配置备份。
3. 为 sing-box 保存实现校验、原子替换、健康检查和回滚。
4. 为单个 VPN 出口实现完整启动/停止清理函数及状态记录。
5. 增加服务重启恢复测试和 Alpine OpenRC 测试。
6. 增加“配置状态、服务状态、链路状态”三个独立字段。

完成这一迭代后，再开始拆分 `vpngate_manager.py` 和重构 Web UI。这样可以先建立可靠行为和测试保护，再改变代码组织，降低持续开发中的回归风险。
